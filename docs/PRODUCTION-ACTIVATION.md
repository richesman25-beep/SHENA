La PR #3 a été fusionnée par le propriétaire. Cette préparation lui succède, sans nouvelle fusion automatique. Aucun SQL, compte, paiement ni fichier Production n'a été modifié par cette phase.

Chaque fichier demande une approbation propre, une cible identifiée et une attestation de restauration associée au SHA256 du manifeste de sauvegarde. Les paramètres SQL sont **déclaratifs** : ils ne prouvent pas eux-mêmes la restauration. Aucun build, workflow ou déploiement n'exécute les migrations. Le générateur hors base est `scripts/prepare-production-activation.py`; son option --check vérifie seulement les fichiers.

Les helpers SECURITY DEFINER ont un propriétaire explicite, des références qualifiées et search_path fixé ; les droits PUBLIC sont retirés. Le helper Storage exposé à anon ne retourne que l'identité admin du demandeur, sans UUID arbitraire. Les mises à niveau des helpers arrêtent l'installation si leurs corps initiaux ont été modifiés. Les autres politiques Storage ne sont pas remplacées. Les clients ne peuvent pas rendre publics les buckets protégés, même si une ancienne politique est large. Les ACL natives Storage dangereuses font arrêter la proposition pour un correctif séparé après inventaire ; aucune permission système n’est modifiée implicitement.

## Sauvegarde et restauration — prérequis non satisfaits

1. Avec un accès opérateur, exécuter l'inventaire préparé en lecture seule : `scripts/audit-production-access.py --output CHEMIN_PRIVE_HORS_GIT`. Il peut aussi lire les métadonnées des sauvegardes du fournisseur. Aucun DDL/DML ; résultats privés, jamais dans Git.
2. Examiner tous les rôles admin existants et confirmer leurs titulaires avant installation ; aucun compte non identifié ne doit gagner des droits par la nouvelle politique. Identifier une sauvegarde complète de la base : schéma, données, Auth, fonctions, politiques et privilèges pertinents. Les sauvegardes DB Supabase **n'incluent pas les octets des fichiers Storage**.
3. Sauvegarder séparément tous les objets de tous les buckets, y compris privés, leurs chemins et checksums ; réconcilier l'inventaire source après copie pour détecter les changements concurrents. Utiliser une destination privée chiffrée autorisée.
4. Restaurer hors Production, isoler les intégrations, emails, tâches planifiées et paiements. Vérifier les tables, permissions/RLS et les octets de chaque fichier restauré. Ne jamais exposer publiquement la copie des données privées.
5. `scripts/check-backup-artifacts.py` contrôle l'intégrité des archives et des copies Storage restaurées. Il **ne certifie pas** la restauration PostgreSQL ni le service Storage ; les essais de services et preuves doivent être examinés séparément. SHA256 prouve l'intégrité, pas la confidentialité.

Aucun jeton Supabase opérateur n'est trouvé dans les accès actuels ; le champ SUPABASE_ACCESS_TOKEN est préparé dans le brouillon sécurisé, sans réinitialiser Vercel. Renseigner ce nouvel accès puis enregistrer/publier l'environnement est indispensable pour l'audit réel. Un accès SQL/Auth/Storage équivalent convient ; aucune clé secrète dans le navigateur.

## Fondateurs et activation séparée

- `scripts/prepare-founder-roles.py` produit un script privé pour deux emails confirmés par le propriétaire. Il exige deux comptes Auth réels distincts, avec identité et propriété du compte confirmées, email déjà vérifié ; aucun compte, mot de passe intégré ou confirmation d'email n'est créé. Les métadonnées existantes sont préservées et user_metadata ne donne aucun droit. Ne pas assimiler une auto-confirmation Auth à une preuve de propriété : contrôler la configuration réelle et la possession des comptes ; les invitations/récupérations nominatives et la révocation des anciennes sessions passent par Auth et nécessitent un accord distinct.
- L'admin peut préparer les PDF en quarantaine, fournir le SHA256 correspondant à un rapport de contrôle, puis créer une copie privée immuable. Le serveur vérifie les octets et le hash ; aucun antivirus automatique n'est simulé. Un second admin approuve ou révoque la version.
- `scripts/prepare-commerce-enablement.py` écrit un script privé paramétré par la durée réelle de réservation et les comptes marchands validés. Il exige les tests de sécurité examinés, deux admins vérifiés, les zones/frais réels pour les produits physiques et pg_cron déjà audité. Il prépare l'expiration automatique des réservations impayées, avec restitution de stock idempotente. Aucun cron n'est installé ou exécuté ici.
- Les coordonnées d'encaissement sont réservées à une configuration opérateur approuvée ; une revue de paiement les photographie dans le dossier. Une référence et une capture ne prouvent pas un paiement : deux admins vérifient réellement l'encaissement. Aucune API MonCash, NatCash ou carte n'est inventée ; cartes et paiements automatiques restent désactivés.
- Après les installations approuvées et l’attribution des comptes, le mode commerce peut être préparé avec les drapeaux DB toujours faux pour permettre aux admins de saisir les zones/frais. Le script d’activation n’est produit qu’avec les décisions marchandes et les preuves de sécurité ; aucun client ne peut se donner cette autorisation.
- Les modes Vercel Production restent disabled. Leur activation future demande SHENA_DEPLOYMENT_TARGET=production et le mode production-reviewed, ainsi que les drapeaux validés en base. Le mode digital est indépendant. Aucune de ces valeurs n'a été activée par cette phase.
- Les liens client sont issus du JWT utilisateur et des RLS Storage, sans service_role. Seul l'acheteur vérifié d'une commande réellement payée peut obtenir une version approuvée ; le lien signé expire sous 60 secondes. Une révocation empêche les nouveaux liens ; un lien déjà émis peut subsister jusqu'à son expiration. PDF uniquement pour ce MVP ; autres formats non activés.

## Validation et retour arrière

Les tests utilisent des comptes/objets/paiements **synthétiques dans PostgreSQL local en mémoire**, sans appel monétaire ou écriture distante. Ils ne prouvent pas la configuration Supabase actuelle. Le correctif ACL final est analysé statiquement, sans tentative TRUNCATE Production.

Les migrations sont transactionnelles par fichier, avec lock_timeout court et arrêt sur schéma inattendu. Une erreur avant COMMIT doit annuler ce fichier. Si 00 réussit puis 01 échoue, la lecture reste disponible et les grants dangereux restent retirés. Ne jamais restaurer aveuglément TRUNCATE ni désactiver RLS pour débloquer une erreur.

Après installation persistante, arrêter d'abord les nouveaux flux avec les drapeaux applicatifs/DB, conserver les données et le journal, puis préparer une réparation ciblée approuvée. Un retour arrière du code ne restaure pas le schéma. Aucune suppression de table/bucket ni restauration par écrasement de Production n'est proposée comme retour arrière automatique.

Contrôles locaux de cette préparation : TypeScript, lint, formatage et build réussis ; 86 tests TypeScript/PostgreSQL locaux réussis, 1 test ACL volontairement non exécuté ; 19 contrôles SQL/outils ; 13 parcours publics démo, 3 sans configuration et 20 admin/commandes sur fixture isolée réussis. Aucun de ces résultats ne certifie les sauvegardes, RLS ou paiements de Production.
