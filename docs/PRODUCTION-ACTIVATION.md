## Fondateurs et activation séparée

- `scripts/prepare-founder-roles.py` produit un script privé pour deux emails confirmés par le propriétaire. Il exige deux comptes Auth réels distincts, avec identité et propriété du compte confirmées, email déjà vérifié ; aucun compte, mot de passe intégré ou confirmation d'email n'est créé. Les métadonnées existantes sont préservées et user_metadata ne donne aucun droit. Ne pas assimiler une auto-confirmation Auth à une preuve de propriété : contrôler la configuration réelle et la possession des comptes ; les invitations/récupérations nominatives et la révocation des anciennes sessions passent par Auth et nécessitent un accord distinct.
- L'admin peut préparer les PDF en quarantaine, fournir le SHA256 correspondant à un rapport de contrôle, puis créer une copie privée immuable. Le serveur vérifie les octets et le hash ; aucun antivirus automatique n'est simulé. Un second admin approuve ou révoque la version.
- `scripts/prepare-commerce-enablement.py` écrit un script privé paramétré par la durée réelle de réservation et les comptes marchands validés. Il exige les tests de sécurité examinés, deux admins vérifiés, les zones/frais réels pour les produits physiques et pg_cron déjà audité. Il prépare l'expiration automatique des réservations impayées, avec restitution de stock idempotente. Aucun cron n'est installé ou exécuté ici.
- Les coordonnées d'encaissement sont réservées à une configuration opérateur approuvée ; une revue de paiement les photographie dans le dossier. Une référence et une capture ne prouvent pas un paiement : deux admins vérifient réellement l'encaissement. Aucune API MonCash, NatCash ou carte n'est inventée ; cartes et paiements automatiques restent désactivés.
- Après les installations approuvées et l’attribution des comptes, le mode commerce peut être préparé avec les drapeaux DB toujours faux pour permettre aux admins de saisir les zones/frais. Le script d’activation n’est produit qu’avec les décisions marchandes et les preuves de sécurité ; aucun client ne peut se donner cette autorisation.
- Les modes Vercel Production restent disabled. Leur activation future demande SHENA_DEPLOYMENT_TARGET=production et le mode production-reviewed, ainsi que les drapeaux validés en base. Le mode digital est indépendant. Aucune de ces valeurs n'a été activée par cette phase.
- Les liens client sont issus du JWT utilisateur et des RLS Storage, sans service_role. Seul l'acheteur vérifié d'une commande réellement payée peut obtenir une version approuvée ; le lien signé expire sous 60 secondes. Une révocation empêche les nouveaux liens ; un lien déjà émis peut subsister jusqu'à son expiration. PDF uniquement pour ce MVP ; autres formats non activés.

## Validation et retour arrière

Les tests utilisent des comptes/objets/paiements **synthétiques dans PostgreSQL local en mémoire**, sans appel monétaire ou écriture distante. Ils ne prouvent pas la configuration Supabase actuelle. Le correctif ACL exact est aussi exécuté dans PostgreSQL embarqué local (version 18), sur une reproduction synthétique : SELECT reste autorisé, les sept autres privilèges effectifs sont refusés, et TRUNCATE/INSERT/UPDATE/DELETE échouent sans modifier les lignes. Cela ne remplace pas une restauration complète ni un essai Supabase natif PostgreSQL 17 ; aucune tentative TRUNCATE Production.

Les migrations sont transactionnelles par fichier, avec lock_timeout court et arrêt sur schéma inattendu. Une erreur avant COMMIT doit annuler ce fichier. Si 00 réussit puis 01 échoue, la lecture reste disponible et les grants dangereux restent retirés. Ne jamais restaurer aveuglément TRUNCATE ni désactiver RLS pour débloquer une erreur.

Après installation persistante, arrêter d'abord les nouveaux flux avec les drapeaux applicatifs/DB, conserver les données et le journal, puis préparer une réparation ciblée approuvée. Un retour arrière du code ne restaure pas le schéma. Aucune suppression de table/bucket ni restauration par écrasement de Production n'est proposée comme retour arrière automatique.
