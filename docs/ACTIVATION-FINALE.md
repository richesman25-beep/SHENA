# Terminer l'activation SHENA

1. **Contrôles** : attendre les deux jobs storefront réussis sur la tête actuelle de la PR nº 4. Le panier de test est initialisé hors React pour éviter son écrasement pendant l'hydratation ; les captures d'échec admin sont conservées comme artefacts CI. Ne pas fusionner pour contourner un échec.
2. **Sauvegarde** : approuver séparément la requête temporaire read_only décrite dans [le plan](proposals/production-activation/BACKUP-READONLY-PLAN.md). Vérifier les droits réels, réaliser le dump PostgreSQL et la copie Storage chiffrés, transférer vers une destination privée durable autorisée et garder la clé dans un gestionnaire séparé. Restaurer base et Storage hors Production et vérifier les accès/données. Tant que ces preuves manquent, aucun script persistant.
3. **SHENA Admin** : après validation de la sauvegarde et accord explicite sur chaque fichier et son empreinte, appliquer dans l'ordre 00-products-acl puis 01-admin ; attribuer les deux comptes fondateurs existants avec le script privé examiné. Le correctif ACL ne modifie ni les produits ni leur politique SELECT. Examiner/approuver le PATCH Auth proposé pour l'origine et les callbacks réels. Tester la connexion des deux fondateurs, les refus client/anon et une opération administrateur autorisée. Aucun mot de passe intégré, aucune auto-attribution par user_metadata.
4. **Commandes et paiement manuel** : après accord, installer 02-commerce et 03-storage, en laissant tous les drapeaux désactivés. Le correctif ACL natif Storage 02-storage-acl n'est pas nécessaire selon l'inventaire actuel et ne doit pas être exécuté par habitude. Renseigner les véritables zones/frais et comptes d'encaissement ; valider l'expiration des réservations, les prix serveur, stocks, idempotence et journal. pg_cron nécessite son propre accord d'installation. Contrôler les paiements réellement reçus avec deux administrateurs distincts ; une référence ou une capture ne suffit pas. Activer séparément les commandes puis le paiement manuel uniquement après ces contrôles et accord du propriétaire. Aucune API de paiement automatique ni carte activée.
5. **Digital et publication** : après accord, installer 04-digital-delivery, préparer les vrais fichiers privés et obtenir leur double approbation. Tester sur environnement isolé le refus avant paiement, pour un autre acheteur et après révocation, puis l'accès temporaire du seul acheteur autorisé après paiement vérifié. Activer le drapeau digital séparément après validation. La fusion de la PR et la promotion Vercel Production exigent ensuite l'accord du propriétaire ; ne pas activer tous les flux au moment de la fusion.

Les scripts exacts et risques sont indexés dans [PRODUCTION-ACTIVATION.md](PRODUCTION-ACTIVATION.md). Aucun build ni workflow n'exécute de migration. Pour arrêter un flux après activation : désactiver ses drapeaux applicatifs/DB, préserver commandes, fichiers et journal, puis préparer une réparation ciblée approuvée ; ne pas rétablir TRUNCATE ou désactiver RLS.
